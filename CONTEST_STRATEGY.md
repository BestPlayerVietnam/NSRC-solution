# NSRC: постоянные условия основного тура

Усиление SLA 13 ноября. Добавлен CPU-предиктор времени по модели и домену с начальными оценками из 989 исторических API-вызовов. Точечный прогноз и эмпирическая верхняя оценка длительности уточняются по собственным наблюдениям текущего процесса. Истории ограничены 32 наблюдениями каждого типа на область модели и домена. Таймауты и неизвестный usage учитываются отдельно, активное время задачи исключает ожидание других задач и transport backoff. При запасе времени сохраняется прежний порядок по ценности токенов. В адаптивном режиме при дефиците задачи и продолжения сравниваются по ожидаемой награде и максимальной доле токенов либо времени от оставшихся ресурсов. В адаптивном режиме лимит генерации уменьшается по точечному прогнозу оставшегося времени. Абсолютный deadline ограничивает каждый физический запрос. Повтор обрезанной генерации останавливается, когда реально достижимый cap уже не растёт. SQL и pytest учитывают deadline, включая подготовку временной копии файлов. Состояние отложенной задачи сохраняется и с выключенным confidence.

Релиз использует `--sla-policy off` по умолчанию. Совместное ранжирование и допуск по времени доступны через явный `--sla-policy adaptive`. Прогнозы времени и общие ограничения API и инструментов работают в обоих режимах. `--time-limit` принимает положительное число до 3300 секунд, по умолчанию 3300. Начало отсчёта предшествует чтению task metadata. Новый policy suffix `|sla-v3` явно отмечает перенос прежних cost artifacts. Прогнозы и эмпирические запасы времени являются эвристическими. Синхронные файловые операции проверяют deadline кооперативно. Прошли 37 модульных и 34 независимых интеграционных проверок SLA. Завершены три цикла API-проверок на всех четырёх моделях. В последнем сравнении при 90 секундах получены off/adaptive баллы 27/27, 26/27, 20/22 и 25/18 для 3.6 plain, 3.8 plain, 3.6 reasoning и 3.8 reasoning. Максимум 31 балл. Потеря семи баллов у основной 3.8 reasoning определила выбор off для релиза. Последний набор содержит 12 свежих публичных групп и четыре повторённых отрицательных контроля. Универсальный прирост качества остаётся неподтверждённым. Итоги сохранены в experiments/SLA_RESULTS_2026-11-13.json, предыдущие версии имеют отдельные отчёты. Актуальное уточнение пользователя от 12 ноября: **экспериментальных прогонов может быть сколько угодно; лимит 100 000 приведённых токенов действует на один отдельный пайплайн одной модели, а не накопительно на все эксперименты этой модели**. Каждый новый pipeline получает свой журнал. Исторические журналы сохраняются без обнуления; незавершённый pipeline нельзя выдавать за новый, сбрасывая его расход. Все четыре модели снова участвуют в новых сравнениях. Отдельной квоты токенов на одну задачу нет. Конкурсный лимит остаётся 100 000 на весь конкурсный прогон.


1. На все 100 задач выделяется общий лимит из **BUDGET**, примерно **100 000 приведённых токенов**. Выходные и
   токены рассуждений учитываются полностью; 10 входных равны одному выходному.
2. Сначала решаем задачи, для которых есть проверяемое локальное решение без
   вызова модели. Остальные ранжируем по ожидаемым баллам на токен:
   `reward × P(успех) / оценка_токенов`.
3. Различаем доказанную невыполнимость, неподдерживаемый локальным решателем
   формат и неудачу в пределах лимита. Отсутствие ожидаемого имени файла или
   поля само по себе не доказывает невыполнимость: информация может быть в
   другом месте. Неоднозначные задачи откладываем либо выполняем короткую
   попытку, если её ожидаемая выгода оправдывает расход. Планировщик больше не делает hard-skip по отсутствию привычного файла
   или колонки. Противоречивые тесты дают hard-skip только при узко проверенном контракте
   stateless/deterministic с обязательным built-in integer результатом;
   разные keyword arguments и типы аргументов учитываются. Дополнительные противоречия одного exact immutable результата могут доказываться исчерпывающим ограниченным перебором при явном integrity-контракте.
4. Доступны четыре модели: `qwen3.6-35b-a3b`, её `-noreason` вариант,
   `qwen3.8-27b` и её `-noreason` вариант. В контролируемом эксперименте
   используется одна выбранная модель на весь pipeline; это проверяют и
   runtime, и прокси эксперимента. Переключение моделей разрешено регламентом,
   но включается отдельным режимом `--allow-model-switch` и оценивается отдельно.
5. Формулировки финальных задач будут новыми, но похожими на выданные примеры.
   Правила для конкретных шаблонов должны иметь безопасный переход к общему
   решателю. Поле `expected` примеров не читается рабочим харнессом.
6. После каждого физического вызова сверяем расход с ledger и заново оцениваем
   полезность продолжения. Коррекцию прогноза обновляем после завершения задачи,
   учитывая все её посещения. Ответ сохраняем сразу. Перед каждым запросом
   резервируем расход и уменьшаем лимит генерации по доступному остатку.

Новый протокол: 64 train, 32 calibration, 48 test синтетических задач с разделением семейств и дополнительная панель 100 новых публичных задач (GSM8K, HumanEval, SQuAD2, WikiSQL), включая 20% отрицательных примеров. Протокол, исходники, образ и прогнозы фиксируются до оценки. EBLO проверяется реальными контрпримерами, а его mock reward не считается качеством нашего агента. См. experiments/POLICY_STUDY_PROTOCOL.md и experiments/EBLO_REVIEW.md. Обученные веса старой policy нельзя незаметно выдавать за независимо проверенный прогноз новой policy.
