# Прогноз расхода и выбор задач для NSRC

Обзор на 7 ноября 2026 года. Наиболее подходящий первый вариант для NSRC —
классический предиктор расхода по мотивам TokenCast, отдельная оценка вероятности
успеха и планировщик общего бюджета. Из кодовых харнессов полезны ограниченные
циклы, выбор релевантного контекста, проверка результата и остановка повторов.
Их преимущество на чужом бенчмарке не доказывает преимущество на нашем контесте.

Это исследование и проект доработок. Перечисленные методы ещё не внедрены:
текущие `planner.py` и `run_agent.py` остаются эвристическим baseline.

## Что именно оптимизируем

По локальному [регламенту](TASK/Регламент%20соревнования.md) и условиям команды:

- 100 задач видны сразу; общий бюджет — 100 000 приведённых токенов.
- Цель — сумма наград за правильные сохранённые решения. При равенстве баллов
  важен меньший расход. Низкий MAE сам по себе не обеспечивает хороший результат.
- Расход `C = input / 10 + output_including_reasoning`. Если reasoning уже входит
  в completion, второй раз прибавлять его нельзя. Скидки за кеш нет.
- Есть четыре конфигурации Qwen: две базовые модели и их варианты `-noreason`.
  Локальные нейросети запрещены; регрессия и бустинг разрешены.
- Примерно 15–25% задач невыполнимы; все выданные примеры выполнимы. Набор
  обучения собираем сами. Условия финала будут новыми; возможны другие объёмы
  данных и сочетания требований.
- Прогноз до запуска использует только доступные тогда признаки. Ошибки,
  ответы инструментов и usage текущей задачи принадлежат отдельному прогнозу
  остаточного расхода. Платный пробный запуск нельзя считать бесплатным признаком.

Локальный регламент основного тура конкретнее ранней переписки: четыре режима,
запрет локальных нейросетей, версия openJiuwen на выбор команды. Поэтому готовые
нейронные маршрутизаторы нельзя подключать только на основании разрешения
переиспользовать чужой код из раннего сообщения.

эксперимент — простой предиктор до запуска. Композицию расхода и роста контекста
стоит добавлять после появления многоходовых трасс, отдельно проверяя пользу.
[Источник: абляции TokenCast](https://arxiv.org/html/2609.35760v2).

Для реализации доступны обычные CPU-методы:
[LightGBM Quantile](https://lightgbm.readthedocs.io/en/stable/Parameters.html)
и [CatBoost Quantile/MultiQuantile](https://catboost.ai/docs/en/concepts/loss-functions-regression).
Сравнивать стоит с регуляризованной регрессией и простыми медианами по группам.
Шесть наблюдений не позволяют обоснованно выбрать сложный алгоритм.

Полную трассу следует хранить отдельно от контекста, посылаемого модели;
вызовы компрессора учитывать отдельно, как показывает
[пример OpenHands condenser](https://github.com/OpenHands/software-agent-sdk/blob/main/examples/01_standalone_sdk/14_context_condenser.py).

Наш расчёт окупаемости платного summary: если он потребляет `I_s` входных и
`O_s` выходных токенов, а в следующих `n` вызовах экономит по `delta_I` входных,
то необходимо `n * delta_I > I_s + 10 * O_s`. Это ещё не учитывает потерю
информации и дополнительные шаги. Для коротких задач сначала стоит проверить
бесплатный отбор и маскирование контекста.

Загрузка всех инструкций тоже не является улучшением по умолчанию:
в [SWE-Skills-Bench v2 от 27 октября 2026](https://arxiv.org/abs/2603.15401v2)
92 из 98 skills не дали статистически значимого эффекта; средний pass ratio
изменился с 76,6% до 76,9%. Каждое расширение нужно проверять парным сравнением.

Лицензии в таблицах относятся к указанным репозиториям. Они не описывают
автоматически лицензии всех зависимостей и датасетов. Чужой код в NSRC в рамках
этого исследования не копировался.

## Предлагаемая архитектура NSRC

Ниже — инженерный проект по результатам исследования, а не измеренный выигрыш.

### Два предиктора с явным контрактом

До первого LLM-вызова сохраняем неизменяемый снимок признаков и для каждого
варианта `(модель, маршрут, лимит, версия харнесса)` прогнозируем:

- ожидаемый расход `E[C]` для выбора задач;
- квантили `Q50`, `Q90`, `Q95` для оценки хвоста;
- `P(правильное решение в пределах лимита)` для оценки полезности;
- степень недостатка данных для данного семейства/маршрута.

Медиана не равна математическому ожиданию. Обратное преобразование среднего
`log(1+C)` также не даёт автоматически `E[C]`. Выбор функции потерь и
преобразования оцениваем по расходу в исходных конкурсных единицах.

После вызовов отдельный предиктор использует прогресс, ошибки, оставшиеся
проверки и usage. Его точность нельзя смешивать с точностью начального прогноза.
Обновлять оценки для следующих задач по уже завершённым допустимо; исходный
прогноз текущей задачи остаётся в логе неизменным.

### Признаки без нейросетей

Общие: тип, длина условия, TF-IDF слов и символов, модель, reasoning mode,
маршрут, лимиты вызовов/output, версия prompt. Для кода: количество файлов,
AST-функций/ветвей, тестов, размер релевантного контекста. Для данных: схема,
число строк, пропуски, требуемые операции. Для поиска: покрытие сущностей и
полей локальным индексом, число переходов между фактами, неоднозначность.

Награда определяет выбор маршрута, но по регламенту случайна и не является
самостоятельным доказательством сложности. Размер модели также не заменяет
измерение её качества и расхода. Начать можно с одной общей классической
модели с признаками конфигурации и групповой калибровкой, чтобы не дробить
маленькую выборку на множество независимых оценщиков.

### Планировщик задач и повторов

Для каждой задачи рассматриваем ограниченное меню: локальный решатель,
каждая из четырёх моделей с небольшим набором лимитов, обоснованный условный
повтор, отложить/пропустить. Не надо сразу запускать все варианты.

Базовая очередь — `reward * P(success) / E[C]`. Конкурент — multi-choice
knapsack: максимум `sum(reward_i * p_i,a)` при общем бюджете и не более одного
первоначального маршрута на задачу. План пересчитывается после результатов.
Для риска сравниваем запас бюджета и верхние квантили; сумма индивидуальных
Q90 не является строгой совместной гарантией. На малых данных сложный
планировщик обязан превзойти простую очередь на отложенных эпизодах.

Повторная попытка оценивается по дополнительному выигрышу после доступного
сигнала неудачи: `reward * delta_P(success | failure_signal)` против стоимости
дополнительных токенов и альтернативных задач. Уже потраченные токены не
делают следующий повтор выгодным. Текущий порог `reward >= 2/4` — baseline.
В финальном прогоне сигналом может быть провал доступного теста или отсутствие
ответа; скрытый verdict жюри для выбора повтора недоступен.

### Невыполнимость и остановка

Нужны отдельные состояния: `proved_impossible`, `unsupported`, `uncertain`,
`failed_within_cap`, `infrastructure_error`. Отсутствие ожидаемого имени
файла не доказывает отсутствия информации в другом файле. Неудача модели
при коротком лимите не доказывает невозможности решения.

Окончательный skip по доказательству допустим лишь при явном контракте задачи:
например, необходимая информация действительно отсутствует во всём разрешённом
источнике и её нельзя восстановить. Остальные задачи можно отложить из-за
низкой ожидаемой выгоды, сохраняя именно эту причину. Детектор повторов должен
учитывать изменение состояния, а не только совпадение команды.

### Учёт и трассы

До вызова резервируем максимальный оплачиваемый output с reasoning и вход.
При параллельных сессиях резерв общий и атомарный. Символьная оценка не является
доказанной верхней границей токенов. Нужен проверенный tokenizer/формат prompt
либо проверенная консервативная граница; соответствие `max_tokens` reasoning
лимиту надо подтвердить на фактическом proxy.

Сохраняем raw usage, нормализованные input/output/reasoning, cap, finish reason,
модель, маршрут, latency, номер попытки, версию кода, снимок признаков, исходный
прогноз, результат проверки и причину остановки. Различаем фактический usage,
оценку и зарезервированный предел. Без usage нельзя освобождать reasoning-резерв
на основании длины видимого ответа. Учитываем неудачный формат, retries,
компрессию и прочие оплаченные вызовы. В журнал не попадают ключи и заголовки
авторизации.

Метка стоимости — фактический расход выбранной политики до её остановки.
Стоимость достижения правильного решения — другая величина: при timeout/cap
она неизвестна, а не равна расходу остановленного запуска. Не запущенные
варианты и пропуски не становятся нулевыми обучающими метками.

## Что исправить в текущем коде прежде обучения

| Место | Наблюдение | Изменение |
| --- | --- | --- |
| `planner.py: impossible_reason` | Отсутствие `test_*.py`, точного KB-файла или поля приводит к hard skip. Сравнение AST-вызовов не учитывает kwargs и контекст тестов; чистота текущего кода не является требованием к исправленному. | Отделить неподдерживаемый формат от доказанной невозможности; не терять решаемые задачи. |
| `run_agent.py: JiuwenLLM.ask` | Вход оценивается символами; reasoning нормализуется эвристически; при отсутствии usage учитывается видимый ответ. | Явные схемы usage, сохранение raw полей, надёжный резерв до запроса и консервативное согласование после него. |
| `planner.py: estimate/observe` | Усредняются расходы по типу без модели/политики; признаки задачи постепенно вытесняются средним. | Калибровать остатки прогноза с учётом модели и маршрута; сохранять неопределённость малой выборки. |

## Как проверить выигрыш

1. Собирать собственные разнообразные семейства с исполняемыми проверками:
   новые формулировки, размеры, операции, файлы и отвлекающие данные. Нужны
   похожие пары решаемых и невыполнимых задач. Варьировать не только числа.
2. До настройки разделить семейства на train, calibration и закрытый test.
   Все перефразировки и повторы одной исходной задачи держать в одной группе.
   Векторизатор, отбор признаков и гиперпараметры не обучать на test.
3. Начать ограниченным пилотом измерений. Сбалансировать четыре модели;
   на общем поднаборе сравнить их напрямую, повторить часть запусков для оценки
   разброса. Дальше собирать информативные пары, а не полный дорогой перебор.
   Пилот проверяет измерение и дизайн; размер полноценной выборки определяют
   learning curves и интервалы неопределённости.
4. В dev проверять правильность независимым валидатором. В финале скрытых
   verdict нет: public tests — только доступный сигнал, а не полная истина.
   Онлайн обновлять стоимость можно надёжнее, чем вероятность скрытого успеха.
5. Сравнивать одинаковые эпизоды из 100 задач, общий бюджет 100k, одинаковые
   случайно назначенные награды и доли невыполнимых 15/20/25%. Воспроизводить
   весь цикл с учётом retries, резервов, сохранения ответов и времени.
6. Главные метрики: итоговая награда, решённые задачи, расход, исчерпание бюджета,
   ошибочные пропуски и потерянная на них награда. Дополнительно: MAE/WAPE,
   ошибка ранжирования, pinball loss, доля случаев `C <= Q90`, покрытие и ширина
   отдельно заданного калиброванного prediction interval, Brier score
   вероятности успеха, доля остановок по лимиту. Нулевые локальные решения
   выделять отдельно: MAPE около нуля вводит в заблуждение.
7. Проверять отдельно каждую модель, тип задач и незнакомые семейства.
   Интервалы результатов строить по независимым задачам/семействам/эпизодам,
   а не считать каждый tool call независимым примером.
8. Последовательно сравнить: текущий baseline; исправленный учёт/skip;
   классический предиктор; квантильный резерв; выбор модели; knapsack;
   управление контекстом и остановкой. Принимать изменения по приросту награды
   при том же бюджете, а не только по красивой ошибке регрессии.

Порядок внедрения: **учёт и безопасные пропуски → качественные трассы и
отложенная оценка → предиктор расхода/успеха → выбор моделей и повторов →
управление длинным контекстом**. При недостатке данных сохраняем простую
эвристику как fallback. Готового универсального предиктора, который гарантирует
точность на новых задачах и наших четырёх конфигурациях без таких измерений,
рассмотренные источники не дают.
