EBLO review
Four targeted satisfiable fixtures triggered its hard-impossibility rules:
Python1/True equality, mutable state, empty-table COUNT=0, quoted text values
mistaken for column names. Our feasibility checker skipped none of these.
These are counterexamples, not population error rates. Its mock simulator
returns full gold answers despite clipped reported output length; its scalar
reward-minus-token objective differs from the contest reward-first objective.
No EBLO implementation was copied into runtime. See EBLO_REVIEW.md and
eblo_counterexamples.json for reproducible details.

Post-validation runtime hardening
- Local math/CSV/search shortcuts must understand the whole supported question;
  added conditions defer to the general solver. Conflicting structured fields
  also defer. Original eight organizer tasks still pass locally.
- Local parsing/planning/tool errors are isolated per task.
- Repeated standalone UNSOLVABLE markers stop attempts; mixed prose does not.
- SQL outer retries preserve the previous query and actual execution error.
  Previously reasoning retries re-entered model_answer with empty feedback.
  Seen queries persist within a task, and context is isolated by workspace and
  exact instruction. No new per-task cap or neural model was introduced.
- A fresh SQL development probe exposed SQLite integer division in generated
  weighted-average queries and an abstention string returned as a SQL scalar.
  The prompt now explains REAL division; exact scalar UNSOLVABLE is a refusal;
  check=exact_int is enforced with correction feedback. No fuzzy matching or
  automatic rewriting of generated arithmetic is used.

The final image differs from the frozen image that earned178/247. Its software

retroactively assigned to changed code. Cost weights predate SQL feedback
hardening and should be recalibrated with further trajectories before claiming

Limitations of the panel
Adapted public benchmarks may be in model pretraining. Exact source spans can
penalize semantically adequate search answers of different lengths. A posthoc
audit found one source annotation starting inside the number140, labelled
'40 million years ago'. Primary frozen scores were NOT changed after discovery;
public100_label_audit.json records the issue. This panel is useful comparative
evidence, not a representative or noise-free estimate of hidden final accuracy.

SQL audit found nine common positive misses across the three 3.8 configurations:
six source gold queries use COUNT where natural 'total number of...' wording
supports SUM; two differ over row count versus the requested Laps value. One
definite source mismatch, public_875aab8d09299b68, has a hidden gold condition
Fastest Laps=0 absent from its question; the visible filters return two rows.
SQLite executed supplied queries correctly. These annotation/wording issues are
separate from the confirmed lost-feedback bug. Gold and primary scores remain
unchanged. Future SQL cost studies should render unambiguous questions from
validated SQL specifications and reserve fresh source tables for evaluation.

The adaptive 3.8 reasoning public gain is one coding task (+1 reward) plus one
SQL task solved in a single call(+2). The entire +3 is not attributable to retry
behavior. Every arm attempted all 100 tasks, so the full-budget comparison does
not establish improved selection when many tasks must be skipped for cost.
