# Эксперименты NSRC

Доработка SLA проверена в трёх циклах на всех четырёх моделях. Последний цикл
сравнивает `off` и `adaptive` при 90 секундах на 12 новых публичных группах и
четырёх повторённых отрицательных контролях. Для релиза выбрано `off` по результату
основной Qwen 3.8 reasoning. Совместное планирование доступно флагом `--sla-policy adaptive`.
[Результаты SLA](SLA_RESULTS_2026-11-13.json) и
[решение о конфигурации](SLA_RELEASE_DECISION_2026-11-14.json) сохраняют метрики,
историю предыдущих вариантов и доказательство единственной правки default после API.

Проверка предыдущей memory-сборки включает 20 новых задач, все четыре
модели, memory off/revise и два прогона с env `BUDGET=5000.5`.
Результаты и hashes сохранены в [API-отчёте](FINAL_RELEASE_API_2026-11-13.json)
и [сводке релизной валидации](FINAL_RELEASE_VALIDATION_2026-11-13.json).
Генератор, проверка оракулов, заморозка протокола, runner и grader находятся
в `final_release_validation.py`. Они создают локальные исключённые из Git наборы
и журналы. Описание предыдущих циклов ниже сохраняет их исходные условия.

**Текущее разрешение:** число экспериментов не ограничено; 100 000 приведённых токенов на один изолированный pipeline одной модели. Новые журналы: `runs/2026-11-12-policy/<phase>/<arm>/ledger.json`. Все четыре модели доступны для новых прогонов. Старый v1 ledger — неизменяемая история прежнего бюджетного режима; описание первых трёх циклов ниже относится к тому режиму. Нельзя сбрасывать расход незавершённого pipeline.


Разрешённый бюджет: **100 000 приведённых токенов на каждую из четырёх моделей**, максимум 400 000 суммарно. Лимиты независимые, остатки не переносятся. Вход учитывается 1:10, выход с reasoning — полностью. Повторы, ошибки с неизвестным usage и пробные запросы входят в тот же журнал бюджета.

`build_suite.py` строит 160 задач из GSM8K, MBPP sanitized, SQuAD2 и WikiSQL и синтетических невозможных случаев. Разбиение 80 train / 40 calibration / 40 test; по 40 задач каждого домена, 20% unanswerable. Эталоны в `suite/oracle.json` не передаются модели. Варианты одного вопроса/таблицы/статьи не пересекают разбиения. Публичные бенчмарки могли быть в обучении Qwen: результаты не являются оценкой без загрязнения.

`run_experiments.py` вызывает настоящий openJiuwen Model. Python-кандидаты и тесты исполняются только в Docker без сети, host mount и API-ключа. SQL исполняется в отдельной in-memory базе с authorizer и лимитом инструкций. Начальный policy фиксирован: один ответ и максимум одно исправление по публичной проверке, без подсказок скрытого oracle. Все модели получают одинаковые задачи и собственный ledger.

Запуски из корня проекта (ключ только в `LLM_API_KEY`, URL в `LLM_BASE_URL`):

```
python -B experiments/download_sources.py --download
python -B experiments/build_suite.py
python -B experiments/test_experiments.py
python -B experiments/run_experiments.py --validate-only
python -B experiments/run_experiments.py --phase pilot
python -B experiments/run_experiments.py --phase train
python -B experiments/test_predictor.py
python -B experiments/analyze.py freeze
python -B experiments/analyze.py plan-calibration
python -B experiments/run_experiments.py --phase calibration
python -B experiments/analyze.py calibrate
python -B experiments/analyze.py plan-test
python -B experiments/run_experiments.py --phase test
python -B experiments/analyze.py report
python -B experiments/run_experiments.py --report-only
```

JSONL трассы, ответы, usage, остановки, результаты скрытых проверок и возобновляемый журнал расходов сохраняются в `experiments/runs/2026-11-12-v1`. Незавершённый запрос после сбоя остаётся полностью зарезервированным. Не удалять и не обнулять ledger при перезапуске. Эксперименты не запускаются без успешной локальной проверки набора. Сборка контейнера для проверки кода: существующий `nsrc-harness:latest`.

Названия P90 или SOTA не присваиваются эвристике: начальный прогноз записывается как baseline. Частичные результаты и ошибки инфраструктуры не считать правильными пропусками. Точность на скрытом test оценивается отдельно от train, а стоимость незавершённого ответа не является стоимостью его успешного решения.


Основное сравнение заранее фиксируется в `evaluation_panel.json`: 20 calibration и 20 test, по 5 задач каждого домена, одна из них невыполнимая. Все четыре модели начинают эти стадии с одинакового списка. Остальные примеры — дополнительная проверка. Если бюджет не позволяет закончить основной список, неполнота указывается явно; пересечение завершённых примеров — только вторичный анализ.

Лимиты стадий — суммарно до 55k train, 75k calibration, 100k test на модель, включая ранние пилоты. Это верхние пределы, а не обязательный расход. До каждого вызова резервируется консервативный максимум. В резерв входят текущий prompt, служебный запас и два output cap для неопределённой семантики reasoning; этот резерв относится к одному вызову. Следующий вызов резервируется отдельно. На наблюдённых ответах reasoning входит в completion и второй раз не прибавляется.

`predictor.py` обучает классические ridge/logistic либо сглаженные средние. Выбор производится по пяти групповым folds только train; четыре модели и варианты одного семейства остаются в одном fold. Cost оценивается в исходных приведённых токенах. Успех означает правильное решение выполнимой задачи: корректный отказ не приносит баллов. Результаты с неизвестным usage/инфраструктурной ошибкой не становятся точными обучающими метками, но их резерв остаётся в расходе.

`analyze.py` запрещает перезапись замороженных оценщиков. Все прогнозы для отложенной стадии записываются до её запуска. Runner проверяет их наличие, hash артефакта, признаков и своего кода. Calibration на основном списке корректирует только одностороннюю верхнюю границу, используя максимальный остаток внутри source group. При малом числе групп граница может отсутствовать. Это не гарантия суммарного бюджета или переноса на другой набор задач.

Оценщик обучен для экспериментального маршрута `bounded-tool-math-v2`: максимум два вызова, SQL по preview, одно evidence-доказательство для QA, восстановление MBPP-функции и Python/число для математики. Его нельзя молча подставлять в другой production-маршрут и считать проверенным на нём. В исходном харнессе есть локальные решатели и другая стратегия повторов.

Исходные файлы проверяются по SHA-256; если upstream изменился, загрузчик останавливается. Не пересобирайте suite поверх текущего эксперимента: отложенные прогнозы и validation привязаны к hash manifest. Датасеты загружаются только при подготовке на машине разработчика.


`replay.py` фиксирует до test два плана выбора модели/пропуска через multiple-choice knapsack: по среднему прогнозу и по верхней оценке. Награда берётся из task.json, ответы и фактические расходы при выборе недоступны. Offline replay сопоставляет эти решения с уже измеренными траекториями; неизвестные варианты не получают выдуманных исходов. Это не живой конкурсный прогон на 100 задачах. После завершения: `python -B experiments/replay.py evaluate` и `python -B experiments/plot_results.py`.

`sql_alias_diagnostic.py` — отдельный анализ только train: проверяет, сколько первых SQL-ответов становятся корректными после сопоставления естественного имени единственной CSV-таблицы с именем адаптера. Эти результаты не заменяют исходные метрики и не меняют замороженную held-out политику. `answerability_review.json` отмечает неоднозначные исходные формулировки GSM8K; эталоны основного измерения сохраняются.


Второй цикл (`build_fresh_suite.py`, `refine_experiment.py`) использует 40 новых source-групп и тот же `runs/2026-11-12-v1/ledger.json`. Отдельный ledger в папке refinement запрещён кодом. Qwen 3.6 reasoning во втором цикле не вызывается из-за малого остатка. Подбор модельных регрессий использует только прежний train; второй набор — только тест. В fresh suite нормализованы переносы строк CSV, а числовые параметры эталонного SQL приведены к представлению, используемому решателем. Основной solver не меняется.

Для чистой подготовки второго набора:

```
python -B experiments/build_fresh_suite.py
python -B experiments/refine_experiment.py validate
python -B experiments/refine_experiment.py prepare
python -B experiments/refine_experiment.py run
python -B experiments/refine_experiment.py report
python -B experiments/summarize_results.py
```

Генератор не перезаписывает готовый fresh suite. `prepare` не перезаписывает замороженные веса; `run` возобновляет только недостающие случаи и проверяет hashes wrapper, solver, predictor, oracle и Docker image. После изменения образа нужно явно восстановить сохранённый экспериментальный image ID перед повторением старого прогона; новые версии solver требуют отдельного протокола, но сохраняют общий бюджетный ledger.

Готовый сводный отчёт: [RESULTS_2026-11-12.md](RESULTS_2026-11-12.md). Итоговая сборка и проверки записаны в [final_validation.json](final_validation.json). Образ замороженного solver сохранён как `nsrc-experiment-v2:20261112`; `nsrc-harness:latest` содержит последующие исправления рабочего SQL-адаптера.


## Третий цикл: реальный production-контейнер

`build_production_challenge.py` подготовил 24 новые синтетические задачи с внешними hidden checks. `production_compare.py` заморозил два image ID и hashes входов/runner, затем провёл оба solver целиком в Docker через локальный API relay. 8 CPU, readonly root, tmpfs, общий старый ledger. Relay учитывает каждый физический запрос, не получает эталоны и сохраняет исходный arm для поздних ответов. Ключ остаётся на host.

[Результат production-сравнения](PRODUCTION_RESULTS_2026-11-12.md) и [новая итоговая проверка](production_validation.json). Полные записи находятся в `runs/2026-11-12-production/`. Текущий runtime образ — `nsrc-harness:latest` (644MB); старый экспериментальный solver сохранён отдельно.

`RESULTS_2026-11-12.md` и `final_validation.json` — снимок первых двух циклов. Не запускать старый `summarize_results.py` для нового общего итога без расширения чтения журналов: он не включает production/calls.jsonl, тогда как общий ledger уже включает эти расходы. Не смешивать старые обученные cost-модели с новым production-policy.
